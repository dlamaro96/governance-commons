# Local core profile

Run `./dev doctor`, `./dev bootstrap`, `./dev up --profile core`, then `./dev seed --dataset harbor-demo`. Open http://localhost:4310. The browser identity issuer is http://localhost:4311/realms/governance; containers use the explicitly configured internal transport while validating the same canonical issuer. Local HTTP cookies are for this localhost development profile; enterprise TLS qualification remains open.

Bootstrap generates six independent passwords for synthetic users `steward`, `owner`, `consumer`, `auditor`, `summit`, and `engineer`. The five Harbor personas are distinct from the Summit tenant administrator. Read one password locally with `python3 scripts/runtime-credential.py steward`; never paste credentials into issues or evidence. Bootstrap is idempotent and never rotates a running installation silently. Credentials and realm imports live in ignored `.local/` (0700 directory, 0600 files).

The source is a distinct PostgreSQL service/database with a read-only `harbor_reader` role. Only the Python worker and the source initialization boundary receive that source secret. The API, workflow history and site coordinator never receive a source password. Scope is restricted by the local secret to Harbor and the exact source host/database/schema. A network-isolated one-shot initializer copies bootstrap files to service-owned 0600 files in separate per-service volumes because Docker Compose bind mounts do not reliably remap secret file ownership. Keycloak and PostgreSQL run under their upstream non-root service accounts after initialization; Python runs as the local user's numeric UID to read its protected bind-mounted secret. SeaweedFS's upstream entrypoint drops to UID/GID 1000:1000; its S3 identity file is copied into a dedicated object-bootstrap volume with that owner and mode 0600. The unused embedded IAM/STS API is explicitly disabled in this static-credential local profile; product authorization remains in the API. Arbitrary-UID and production hardening qualification is pending.

Only the API and Keycloak publish ports, both on 127.0.0.1. PostgreSQL, OpenSearch, Temporal, S3 and the Python execution endpoint remain in the project Docker network. OpenSearch security is disabled in this isolated local profile; the application enforces tenant filtering and canonical authorization. This profile must not be exposed to an untrusted network or represented as a qualified production installation.

`./dev down` preserves volumes. There is no destructive reset command yet; backup/restore and isolated reset qualification remain required work. Do not use broad prune operations. `./dev status` returns only this project's service state. `./dev test --suite connectors` executes unit and real source tests inside the actual Python image, then creates an isolated synthetic test table to verify table/column rename identity, permission-reduction failure, and deletion completeness. It removes that test table in a finally block. Run this suite without concurrent demo scans. Its host unit-only invocation explicitly skips source tests when the source secret is absent.

The core startup budget is provisionally 4 vCPU and 5.5 GiB Docker RAM. Doctor requires 8 GiB free disk when any dependency or application image is missing, or 2 GiB with all images cached. Application and Python builds run serially and check the 2 GiB stop floor before each build. These are conservative admission budgets, not measured minimum-resource support claims. The initial attempt with only 5 GiB free exhausted the host disk during image extraction; startup was halted and the failure is not a successful profile qualification. RAM, disk, architecture and each qualified command must be recorded with release evidence.

The local volume limit is 16 slots of 64 MiB each, allowing the internal filer collection, application bucket and temporary qualification bucket to coexist; four slots alone were consumed by the internal collection. The master grows one local unreplicated volume at a time instead of seven per collection. These are allocation limits, not preallocated disk or a scale qualification. The S3 probe allows 20 seconds per request because upstream defers initial allocation for 15 seconds after leader election to prevent volume-ID reuse; that protection stays enabled.

Seaweed readiness requires a readable credential file as its runtime user, an elected master leader, a registered volume server, the filer endpoint and anonymous S3 denial. The launcher additionally signs ListBuckets with the API service's existing S3 environment and verifies invalid signatures are denied. `./dev test --suite object-store` creates an isolated synthetic bucket, writes and reads 64 KiB of generated bytes, checks anonymous/invalid access denial, and deletes its test object and bucket. It uses the existing API image through stdin and publishes only bounded statuses; no secret or signed request is exported. This gate is mandatory in hosted behavior CI. It qualifies local S3 infrastructure only, not product document/evidence workflows or tenant-specific object policies. Earlier core-runtime and core-recovery reports checked only the master HTTP endpoint and did not qualify authenticated S3 readiness.

The pinned Temporal server image does not initialize databases. A matching digest-pinned admin-tools job applies the bundled PostgreSQL schemas before server startup; another creates the default development namespace after readiness. The tracked dynamic configuration file explicitly accepts server defaults. Both jobs can run again without clearing history.

`./dev test --suite recovery` requires an idle synthetic local installation. It verifies two seed invocations leave seeded identities and memberships unchanged, gracefully stops and starts this project's services while preserving all volumes, and compares canonical-data digests before and after. It writes sanitized evidence under `docs/verification/core-recovery.json`. Run it after browser and other mutating tests finish. This checks restart persistence, not a clean installation, backup restore, version upgrade, failure during an active scan, or an enterprise availability target.

After a real application scan succeeds, `./dev test --suite histories` inspects that completed Temporal workflow. It requires ID-only workflow/activity inputs, status/count-only results, and checks that locally generated credentials occur in neither raw history nor decoded payloads. Only event field names and the history checksum are recorded in `docs/verification/core-temporal-payloads.json`; raw history is not exported. Failed/retried histories and other workflow types need their own tests.

`full`, `ai-local`, complete acceptance, upgrade, backup/restore, Kubernetes, benchmark and support-bundle commands remain explicit failures until implemented. They are required programme scope, not optional omissions. Temporal orchestrates scans through the workflow worker and site activity; source-specific work runs in the separate uv-managed Python container. Workflows contain IDs and sanitized completion counts only.

Pinned upstream sources: [OpenSearch downloads](https://opensearch.org/downloads/), [Temporal server](https://github.com/temporalio/temporal/releases), [Temporal image startup](https://github.com/temporalio/docker-builds/blob/main/docker/entrypoint.sh), [Keycloak](https://www.keycloak.org/), [SeaweedFS](https://github.com/seaweedfs/seaweedfs), [Python image](https://hub.docker.com/_/python), [uv](https://github.com/astral-sh/uv). Exact images are digest-pinned in compose and the Python Dockerfile. Tested architecture and observed versions belong in the evidence manifest; a multi-architecture manifest alone is not runtime qualification.

Reference-code imports accept bounded UTF-8 JSON or CSV, up to 262144 bytes and 256 rows. Preview reconciles against the current published version; applying it changes only the authoring draft. Submission still requires the normal independent approval and publication workflow. To scan uploads before parsing or database work, set `GC_UPLOAD_SCANNER_ENABLED=true`, `GC_UPLOAD_SCANNER_HOST` and `GC_UPLOAD_SCANNER_PORT` in the Compose environment to an operator-controlled ClamD INSTREAM endpoint. The scanner connection must remain on a trusted private network because ClamD TCP does not authenticate the transport. When enabled, unavailable, malformed, timed-out or rejected scans block the upload; a scan has a five-second total deadline. This profile does not provision a scanner engine; an actual engine and signature-update qualification remain separate from the tested protocol adapter.
