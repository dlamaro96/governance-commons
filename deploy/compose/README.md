# Local core profile

Run `./dev doctor`, `./dev bootstrap`, `./dev up --profile core`, then `./dev seed --dataset harbor-demo`. Open http://localhost:4310. The browser identity issuer is http://localhost:4311/realms/governance; containers use the explicitly configured internal transport while validating the same canonical issuer. Local HTTP cookies are for this localhost development profile; enterprise TLS qualification remains open.

Bootstrap generates six independent passwords for synthetic users `steward`, `owner`, `consumer`, `auditor`, `summit`, and `engineer`. The five Harbor personas are distinct from the Summit tenant administrator. Read one password locally with `python3 scripts/runtime-credential.py steward`; never paste credentials into issues or evidence. Bootstrap is idempotent and never rotates a running installation silently. Credentials and realm imports live in ignored `.local/` (0700 directory, 0600 files).

The source is a distinct PostgreSQL service/database with a read-only `harbor_reader` role. Only the Python worker and the source initialization boundary receive that source secret. The API, workflow history and site coordinator never receive a source password. Scope is restricted by the local secret to Harbor and the exact source host/database/schema. A network-isolated one-shot initializer copies bootstrap files to service-owned 0600 files in separate per-service volumes because Docker Compose bind mounts do not reliably remap secret file ownership. Keycloak and PostgreSQL run under their upstream non-root service accounts after initialization; Python runs as the local user's numeric UID to read its protected bind-mounted secret. The local SeaweedFS image retains its upstream default UID; arbitrary-UID and production hardening qualification is pending.

Only the API and Keycloak publish ports, both on 127.0.0.1. PostgreSQL, OpenSearch, Temporal, S3 and the Python execution endpoint remain in the project Docker network. OpenSearch security is disabled in this isolated local profile; the application enforces tenant filtering and canonical authorization. This profile must not be exposed to an untrusted network or represented as a qualified production installation.

`./dev down` preserves volumes. There is no destructive reset command yet; backup/restore and isolated reset qualification remain required work. Do not use broad prune operations. `./dev status` returns only this project's service state. `./dev test --suite connectors` executes unit and real source tests inside the actual Python image; its local unit-only invocation explicitly skips source tests when the source secret is absent.

The core startup budget is provisionally 4 vCPU and 5.5 GiB Docker RAM. Doctor requires 8 GiB free disk when any dependency or application image is missing, or 1.5 GiB with all images cached. These are conservative admission budgets, not measured minimum-resource support claims. The initial attempt with only 5 GiB free exhausted the host disk during image extraction; startup was halted and the failure is not a successful profile qualification. RAM, disk, architecture and each qualified command must be recorded with release evidence.

`full`, `ai-local`, complete acceptance, upgrade, backup/restore, Kubernetes, benchmark and support-bundle commands remain explicit failures until implemented. They are required programme scope, not optional omissions. Temporal orchestrates scans through the workflow worker and site activity; source-specific work runs in the separate uv-managed Python container. Workflows contain IDs and sanitized completion counts only.

Pinned upstream sources: [OpenSearch downloads](https://opensearch.org/downloads/), [Temporal server](https://github.com/temporalio/temporal/releases), [Temporal image startup](https://github.com/temporalio/docker-builds/blob/main/docker/entrypoint.sh), [Keycloak](https://www.keycloak.org/), [SeaweedFS](https://github.com/seaweedfs/seaweedfs), [Python image](https://hub.docker.com/_/python), [uv](https://github.com/astral-sh/uv). Exact images are digest-pinned in compose and the Python Dockerfile. Tested architecture and observed versions belong in the evidence manifest; a multi-architecture manifest alone is not runtime qualification.
