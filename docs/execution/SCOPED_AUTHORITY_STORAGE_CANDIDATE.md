# Scoped authority storage protocol candidate

Status: **ROOT-ADOPTED DESIGN / IMPLEMENTATION CANDIDATE — NOT IMPLEMENTED, NOT ACTIVATED, NOT VERIFIED.** Prepared 2026-11-16. Root adopted the seven storage decisions in this document after reviewing [the authority contract candidate](SCOPED_AUTHORITY_CONTRACT_CANDIDATE.md), inspected SHA256 `443a6b796354f6b8daf2dea3b98e83426faca19d4c57139e89a526c533433802`. This document fixes the proposed protocol envelopes and trust boundaries for subsequent shared-contract review. It allocates no migration number, changes no deployed role or permission, and authorizes no runtime activation. The full [BUILD_SPEC](../product/BUILD_SPEC.md) remains governing; the authority candidate's requirement mapping, 103 compatibility actions, 21 administration actions, field/service distinctions and mandatory gates remain unchanged.

Applied SQL001–011, existing canonical snapshot formats, audit envelopes, idempotency namespaces and SQL007–011 receipts/hashes remain immutable. Additive authority companions preserve those bytes. Current execution status remains in [STATE](STATE.md).

## 1. Trust and role matrix

Database login credentials authenticate the executor generation; a caller-provided generation number, `application_name`, HTTP label or `gc.*` setting does not. Every public entrypoint checks the original `session_user` role OID against an immutable protected executor registration and current allowed generation. `current_user` is unsuitable for that proof because a SECURITY DEFINER function changes it. Role membership, inheritance and `SET ROLE` cannot provide a path into a definer or another generation. Login roles have `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`, no schema CREATE and no ownership of protected objects.

| Role family | Permitted authority | Explicit boundary |
|---|---|---|
| Existing migration owner | Reviewed forward DDL and controlled installation/recovery | Its credential is absent from every API, broker, worker, projector and site process. It is not an ordinary runtime test role. |
| `gc_authn_definer` (NOLOGIN) | Enumerated reads of configured issuers, provisioned identities and memberships; reviewed login-attempt/session/provenance operations | No tenant content, policy administration, decision minting or public raw session-table reader. |
| `gc_authority_definer` (NOLOGIN) | Enumerated policy/context/claim/companion access; complete integrity reads and the exact canonical writes needed by closed adapters | Forced tenant RLS, fixed search path, explicit tenant predicates and protected-context checks remain mandatory; no public unrestricted cohort helper. |
| `gc_a1_api_gN` (LOGIN) | Human protected reads/commands; exact-session logout and tenant selection | No base-table/session-table SELECT or DML, sequences, issuer operations, service claim functions or definer membership. |
| `gc_a1_login_gN` (LOGIN) | Login-attempt and verified-session issuance functions only | Dedicated trusted OIDC broker; no tenant content or human/service command execution. |
| `gc_a1_service_gN` (LOGIN) | Authenticated service gateway reads, claims, lease redemption and closed service commands | Separate pool from human requests; each call additionally proves the canonical service credential/assignment. No generic raw tenant access. |
| `gc_a1_projection_gN` (LOGIN) | Only registered projector consumption/acknowledgement adapters | No human session issuance, source secrets or general service effects. A projector registration is not a source-execution credential. |

`gN` denotes a real separately provisioned role/credential generation, not a dynamically accepted name prefix. An explicit registry maps exact role OIDs to executor kind, generation, active status and allowed adapter set. New deployment processes receive only the appropriate generation credential. Sites and Python workers receive **no database credential**; they use authenticated gateway channels.

Definer functions use a fixed trusted search path and fully qualified objects, and run with row security on. Revoke PUBLIC execution/default execution, old runtime function grants, unintended view access, table/sequence privileges and inherited permissions before activation. Grants enumerate complete function signatures, not just names; accidental overloads cannot inherit authority. Table owners remain non-runtime and non-BYPASSRLS; forced RLS continues to protect tenant data, including integrity helpers. The protected operation derives the trusted tenant setting used by legacy tenant policies. Runtime-selected GUC values alone never establish a context. Do not add scoped filtering to private integrity queries that would hide a cycle, cardinality member or zero-edge participation obligation.

## 2. Exact protocol conventions

All functions below are proposed SQL entrypoints. They are not implemented functions. UUIDs, counters, digests, timestamps and registry handles use the authority candidate's strict primitives. All JSON objects reject undeclared keys; JSON arguments are bounded against the relevant adopted adapter budget before retained materialization. `adapter_id`, `effect_kind` and `projectionId` must resolve in closed root-adopted registries. An unknown handle is rejected; there is no dynamic SQL, table-name, field-path or action-prefix dispatcher.

Envelopes returned to the trusted application are distinct from HTTP DTOs. `result` is the exact existing or separately adopted public DTO for the registered projection; wrapping it internally does not add fields to that DTO. `preparation` and effect payloads are exact adapter-specific schemas, not arbitrary accepted JSON. Their catalog remains a prerequisite for implementation.

```ts
type ReadEnvelope = {
  formatVersion: 1; adapterId: string; projectionId: string; result: unknown;
};
type BeginEnvelope =
  | { formatVersion: 1; kind: 'replay'; adapterId: string; projectionId: string; result: unknown }
  | { formatVersion: 1; kind: 'prepared'; operationId: string; adapterId: string;
      deadlineAt: string; preparation: unknown;
      effects: readonly { effectId: string; effectKind: string; payloadHash: string }[] };
type AppliedEnvelope = { formatVersion: 1; operationId: string; effectId: string; applied: true };
type SealedEnvelope = {
  formatVersion: 1; operationId: string; sealed: true; projectionId: string;
  responseHash: string; result: unknown;
};
type SuccessEnvelope = { formatVersion: 1; operationId: string; result: unknown };
```

The `unknown` types above mark references to still-unfrozen registry schemas, **not permissive parser types or implementation placeholders that may ship**. Concrete shared TypeScript unions and SQL shape checks must replace them before an adapter is implemented. Request hashes cover the exact existing outer idempotency body; semantic normalization and plan hashes retain each family's existing distinct rules. Claim/payload hashes are recomputed by storage from independently derived canonical tuples. Matching a caller-supplied hash never proves an outcome.

## 3. Human reads and mutations are separate protocols

| Function signature | Return | Required behavior |
|---|---|---|
| `gc_authority_read(session_hash text, adapter_id text, selector jsonb)` | `ReadEnvelope` JSONB | Derive exact actor/selected tenant from a live session; prove executor generation, session issuance provenance, identity/member activity, current policies and declared fields. Return only the adapter's authorized projection. |
| `gc_authority_command_begin(session_hash text, adapter_id text, idempotency_key text, request_body jsonb, correlation_id text)` | `BeginEnvelope` JSONB | Authenticate, reserve the existing idempotency namespace/key, derive complete canonical scope and subordinate actions, lock and revalidate, then install private exact claims. Exact replay reauthorizes original scope and fields before returning its existing response. |
| `gc_authority_apply(operation_id uuid, effect_id uuid, effect_kind text, payload jsonb)` | `AppliedEnvelope` JSONB | Consume one exact unconsumed operation claim, independently verify payload against the derived expected effect and perform only that effect. No unclaimed insert, delete, patch, history or journal operation is expressible. |
| `gc_authority_command_seal(operation_id uuid)` | `SealedEnvelope` JSONB | Validate the full final canonical state, immutable outcomes, exact required journals and absence of extra effects; seal further canonical writes. Derive the exact response and its registered projection. |
| `gc_authority_command_success(operation_id uuid, response jsonb)` | `SuccessEnvelope` JSONB | Match sealed expected response by value and canonical hash; write the exact legacy idempotency success through a protected path. Recheck final time/authority obligations and return only the permitted response. |

These entrypoints accept no claimed actor, tenant, permission array, approved policy match or caller-selected complete scope. Resource/parent selectors in a legitimate operation body identify requested work; the protected adapter resolves their canonical tenant and actual old/proposed scope. Pure prepared results and simulations remain inputs to comparison, never capabilities.

### Read-only snapshot behavior

`gc_authority_read` is compatible with a real **READ ONLY REPEATABLE READ** transaction. It does not insert a private transaction-context row, obtain mutation row locks or append decision/audit records. It validates session and policy state from that fresh primary snapshot, checks database time for expiry, and performs authorization before counts, facets, limits or payload loading. Each call independently validates its exact session, role registration and projection. Complete audit verification keeps its existing hidden-event check and bounded chain in the same snapshot. A separate best-effort telemetry process cannot be represented as an atomic write within this read-only transaction.

Read authority linearizes at the fresh primary snapshot. Revocation committed before that snapshot is observed; this is not a promise to retract bytes already returned or to reinterpret a long-lived old snapshot as current. An adapter cannot reuse a transaction/snapshot across independent requests. No externally selectable historical snapshot, arbitrary cursor fence or replica lag substitutes for current authority. Cached/index results are filtered under current primary authority and projection rules before disclosure.

### Protected mutation context and phase sequence

Private `authority_operation_contexts` bind at least `{operationId, backendPid, transactionIdXid8, executorRoleOid, executorGeneration, authenticationKind, sessionIdOrCredentialId, sessionTenantAtBegin, actorOrServiceId, tenantId, adapterId, startedAt, deadlineAt, requestHash, canonicalScopeHash, policyEvidenceHash, projectionId, state}`. Authority/effect/field evidence is stored in normalized private companions, with forced tenant RLS, composite FKs and append-only finalized records. Runtime has no direct access. Table names here reserve the design vocabulary; actual table schemas remain subject to the shared storage contract.

Minimum protected records are: `authority_executor_registrations` (exact role OID/kind/generation/status/adapter ceiling); `authority_issuer_registrations` and one-use `authority_login_attempts`; `authority_session_provenance` (new session UUID, unique existing session hash, issuer/attempt proof, selected tenant, session version, expiry/revocation); `authority_operation_contexts`; normalized `authority_operation_scope`, `authority_operation_decisions` and `authority_operation_effects`; and `authority_operation_success_bindings` linking the exact existing tenant/actor/namespace/key/request/response hashes to a finalized operation. Service records add `authority_service_credentials`, `authority_job_claims`, `authority_execution_leases` and action/request-bound `authority_lease_consumptions`. Tenant-owned records use composite tenant keys/FKs and forced RLS; global issuer/executor/identity records are private global trust infrastructure, never runtime-enumerable tenant data. An existing session hash is not itself the new UUID or proof of issuance. No protected record accepts a caller-authored allow result.

A context is usable only by the same original login role, backend and transaction; operation UUID knowledge is insufficient. There is one command family per transaction, no actor/tenant replacement, no nested authority context and no resumption in another transaction. Re-read the canonical session's selected tenant and provenance before protected completion. A session tenant switch cannot retarget an already begun operation.

The order remains: authentication without premature principal locks; existing idempotency reservation; tenant ledger; tenant authority fence; complete model/type/domain/resource lock order; one global UUID-ordered identity share-lock phase; UUID-ordered tenant-membership share locks; ordered exact authentication/claim row locks; current-authority reread; private claims; canonical/revision/journal effects; seal; existing idempotent success; outer `SET CONSTRAINTS ALL IMMEDIATE`; final deadline check; commit. Existing deferred guards also enforce completeness at commit if an untrusted caller omits the explicit final statement. No inner adapter calls final constraints early. Nested SQL007 receipts and SQL009–011 operation guards retain their exact attribution, revision FKs, family isolation and final-state semantics.

Removing base DML requires adapting **every** existing Kysely write and journal/idempotency insertion to protected exact-claim effects. Do not retain a privileged general writer connection as an escape. Existing storage begin/seal functions become private composition helpers or validate the same companion; merely granting their old public signatures to the new runtime would bypass the complete action/resource contract.

Derived effect records include actual before identity/version/tuple, independently computed after tuple, action/resource kind, expected immutable revision, actor/correlation, journal pair and payload hash. Canonical values and outcomes are compared, not hashes alone. Full legacy asset snapshot/metadata values retain their existing valid grammar and physical-byte budgeting; new authority safe-key rules must not reject or silently rewrite unchanged historical payloads. Sealing proves normalized complete scope and exact outcomes, not caller-reported counts.

## 4. Authenticated login bootstrap and session lifecycle

A dedicated broker carries out the existing OIDC authorization-code+PKCE flow and validates state, nonce, configured issuer, audience, permitted RS256 signature, subject and expiry. Its database role is absent from the ordinary human API pool. The DB explicitly trusts this narrow broker's attestation of successful OIDC validation; it does **not** claim to verify JWT signatures itself. Raw ID/access tokens are not persisted as authority proofs.

Proposed issuer entrypoints:

- `gc_authn_attempt_begin(state_hash text, verifier text, nonce_hash text)` returns `{formatVersion:1,attemptId,expiresAt}`. The broker supplies cryptographically random state/verifier/nonce material, storage fixes the configured issuer/client/redirect binding, expiry and executor identity, and no ordinary API role can enumerate/read the attempt table. The verifier is secret and stays in the broker boundary.
- `gc_authn_attempt_consume(attempt_id uuid, state_hash text)` returns `{formatVersion:1,attemptId,verifier,issuerId,clientId,redirectUri,nonceHash,expiresAt}` only to the bound live issuer generation. Consumption is one-use for exchange; a failed exchange requires a new login attempt, preserving the present anti-replay behavior.
- `gc_authn_session_issue(attempt_id uuid, verified_claims jsonb, session_hash text, csrf_hash text)` returns `{formatVersion:1,sessionId,expiresAt,selectedTenantId}`. Exact `verified_claims` keys are `{issuer,subject,audience,nonceHash,idTokenHash,authenticatedAt,issuedAt,expiresAt}`. These are broker-attested claims, never actor UUIDs, role names, permissions or grants. Storage checks configured issuer/audience, original nonce/attempt, DB-time validity and one-use issuance; it resolves provisioned `(issuer,subject)` and selects an actual active canonical membership. Store private issuer-role/generation, attempt, token digest and authentication-time provenance linked to the session.
- `gc_authn_session_revoke(session_hash text, csrf_hash text)` returns `{loggedOut:true}` for that exact authenticated session under its session mutation policy.
- `gc_authn_session_select(session_hash text, csrf_hash text, tenant_id uuid)` returns `{formatVersion:1,sessionId,selectedTenantId}` only for an actual active membership; the UUID is a requested selection, never an assertion of membership. It invalidates old tenant-bound contexts/cursors according to the protected session version and does not change grants.

Raw session/CSRF values are generated with cryptographic randomness at the trusted broker and conveyed only through the established secure cookie/CSRF flow. Both session hashes and credential/lease hashes presented to protected SQL are authentication inputs and are kept out of logs, public evidence and Temporal. Request transport still checks allowed origin, CSRF and HttpOnly session handling. The initial protected operation proves exact session binding again; it does not accept a previously passed `Principal` as authority.

At A1 executor cutover, require fresh authentication and new issuance provenance. Do not retrospectively certify legacy sessions: current legacy `gc_app` can insert session rows, and old rows contain no new broker attestation. Revocation invalidates the session version/provenance rather than deleting immutable business history. Installation authority must provision exact issuer/broker registrations independently of tenant content grants; the administrative/bootstrap authorization process remains an explicit dependency below.

## 5. Revocation, locks and original deadlines

The adopted global identity strategy remains unchanged: identity update itself serializes deactivation; it never acquires tenant ledgers while holding the global identity row. A protected mutation locks the complete globally sorted principal union once and holds identity/member share locks through commit. No later lower UUID append is permitted.

Add an exact authentication lock phase **after** those principal locks: session rows, service-credential rows, job-claim rows and lease rows, in a fixed family order and UUID order within each family. A human operation locks its exact session; a service operation locks its exact credential, claim, parent lease and any child lease. Use current-row share locks sufficient to conflict with revocation/version updates, then reread issuer/executor generation, selected tenant, identity/member/service activity, grant dependencies, credential/claim version and expiry. Hold these locks through commit. A revoke that wins first makes the operation wait/recheck or deny; an operation that wins may finish before the revoke commits. Time expiry still requires fresh database clock checks because time does not wait for row locks.

Logout/session revocation and service credential revocation cannot hold an authentication row and then acquire tenant ledgers or earlier principal locks. A narrow session-only logout may lock/update that session and finish without those later acquisitions. Tenant selection requiring membership checks follows the shared principal-before-session order. Administrative service reassignment/reallocation follows tenant ledger and complete principal order before credential/claim/lease updates. Recovery cannot invent a special inverse lock order.

One DB operation has an original **30-second** budget starting at protected entry; nested helpers and success/replay paths do not restart it. Services pre-arm statement/lock timeouts in separate frontend commands before calling work, and SQL checks the stored remaining deadline at discovery/iteration/materialization/lock/phase boundaries. Expiry at seal/success/deferred completion rolls the transaction back. Direct SQL does not obtain a universal hard wall-clock guarantee merely by changing `statement_timeout` inside an already executing statement. Qualification must separately prove cooperative discovery checks, contention bounds and the actual service pre-armed timer; any uninterruptible stage remains a blocker to claiming its deadline guarantee. Protected profiles remain bounded and do not silently truncate complete scopes.

## 6. Service claims and attenuated worker leases

The gateway validates an actual registered service credential in addition to its own generation-specific DB login. Source/job/site/initiator associations come from canonical records. Dispatch and initial claim need no metadata lease yet; their separate entrypoints do not create a general content context. Current-service safe terminalization remains available under its narrow adopted rules after human revocation/lease expiry, never after service revocation without an explicit recovery-service assignment.

| Function signature | Exact return envelope and purpose |
|---|---|
| `gc_service_read(credential_hash text, adapter_id text, selector jsonb)` | `ReadEnvelope`; only registered dispatch/projector/terminal-status projections authorized for this executor and service. |
| `gc_service_claim(credential_hash text, job_id uuid, correlation_id text)` | `{formatVersion:1,kind:'claimed',leaseId,token,claimVersion,issuedAt,expiresAt,jobDeadlineAt,projectionId,result}` or `{formatVersion:1,kind:'terminal',jobId,terminal:true}` after exact fresh terminal authorization. `result` is the registered assigned-source metadata configuration projection, never a human grant. |
| `gc_service_child_lease(credential_hash text, parent_token_hash text, worker_service_id uuid, correlation_id text)` | `{formatVersion:1,leaseId,parentLeaseId,token,issuedAt,expiresAt}` for the canonical worker bound to this site/source/job. The caller cannot choose actions, audience, expiry or a different job. |
| `gc_service_redeem(credential_hash text, token_hash text, adapter_id text, request_body jsonb)` | `ReadEnvelope` for only the exact permitted metadata/secret-resolution action. A secret-resolution result is the private registered site/source/secret-reference descriptor; the actual source credential remains at its authorized site. |
| `gc_service_command_begin(credential_hash text, token_hash text, adapter_id text, idempotency_key text, request_body jsonb, correlation_id text)` | `BeginEnvelope`; complete/current-authorized service effects use the same exact-claim apply/seal/success protocol as human mutations. |
| `gc_service_terminal_begin(credential_hash text, job_id uuid, idempotency_key text, request_body jsonb, correlation_id text)` | `BeginEnvelope` restricted to safe failure/cancellation; successful result and exact retry are only `{jobId,terminal:true}`. It cannot read configuration, resolve secrets, claim metadata or complete successfully. |

The existing minimal terminal DTO is an intentional new internal projection; old immutable job/audit records are unchanged. No denied caller learns terminal state or existence. A replayed successful completion still needs current service/claim/initiator authorization and its own minimal registered projection; it cannot fall through to the existing unrestricted `jobView` return.

Each opaque bearer has 256 bits of cryptographic randomness; store only SHA-256. The site receives its parent bearer only over an authenticated direct channel. Python receives a distinct child bearer through its authenticated direct channel and presents its own service credential. Store `parentLeaseId` and the exact worker/site audience on the child; its actions, scope and expiry are a subset of the parent. Both parent and child current credential/claim records must remain valid at redemption. No shared site credential, transferred parent token or caller-named audience silently stands in for the Python principal. These child companions are new authority data, not changes to historical receipts.

An attempt lease lasts at most **180 seconds**, matching the current three-minute Temporal activity attempt. It has no in-attempt renewal extending that boundary. A job's original execution deadline is **20 minutes from its first allocated claim**, with at most **five allocated attempts**; retries do not reset either bound. API/database operations remain within the 30-second transaction budget and remaining job/lease time. Queue waiting before the first claim does not spend an execution-attempt budget, and still obeys the separately configured workflow scheduling bound.

Reallocation is allowed only after the old lease expires or an explicitly authenticated abandon/recovery transition revokes it; it increments the canonical claim version and rotates bearers. An old activity cannot complete after reallocation. A transport retry that lost the initial bearer must wait or perform an authorized abandon/reallocation; hashes in Temporal history cannot reconstruct it. Failed/expired claims cannot silently allocate a sixth attempt. After the original job deadline, only the narrowly authorized terminal/recovery path remains.

Temporal carries only non-secret canonical reference IDs. Parent/child bearers, bearer hashes, credentials, source secret references, raw scan payloads and error details never enter workflow/activity inputs, results or heartbeats. Current site/source and initiating-human authority is checked at claim, redemption and successful completion. Native PostgreSQL privileges/destination restrictions and incomplete-scan reconciliation rules remain independent ceilings. Token expiry cannot retract source credentials already placed in worker memory; the local worker must use bounded in-memory execution, observe cancellation/lease expiry, discard results and close source sessions. Do not claim instantaneous revocation of an already issued external credential without a separately qualified native revocation mechanism.

## 7. Atomic executor cutover

The executor boundary changes globally before activating scoped policy for any tenant. First deploy/register the reviewed generation and compatibility grants without granting a new permissive fallback. During a coordinated maintenance boundary, stop old issuer/dispatcher/site/projector admissions, prevent old role login, revoke its base/function/PUBLIC paths, and drain or terminate every old pooled backend and outstanding transaction. Inspect prepared transactions as well as ordinary backends; an unresolved prepared transaction blocks activation and needs an explicit reviewed resolution, never automatic rollback of unrelated work. Password rotation or copying a new numeric generation is insufficient.

Read back the exact role memberships, function/table/default privileges, old connection absence and required executor registrations. Require fresh human sign-in and current service credentials. Only then switch each tenant's protected mode/generation atomically. New executors in compatibility mode use the new protected ingress; no route or service may select the old evaluator after tenant activation. A failed rollout remains closed or receives a forward repair; recovery never restores broad legacy grants. Exercise both existing old connections and newly attempted old-role logins in the isolated qualification.

## 8. Dependencies and qualification still required

Before implementation begins, root must freeze the adapter/projection/field catalog (including the referenced `preparation`, effect and result unions), aggregate authority/principal budgets, authority administrator/issuer/service installation and recovery provenance, exact 21-action administration adapters/retirement impact, and trusted purpose/environment/classification facts. The action registry, model UUID alias, field alias/deny semantics and complete structural visibility are already selected; this document does not reopen or reduce them. No role name, ownership value or seed persona supplies installation or policy administration authority.

Required qualification includes all 1,024 legacy permission subsets across the unchanged 103 actions; pure/SQL/search equivalence; actual nonowner runtime role grants; forged session, issuer, GUC, generation and transaction attacks; alias and field-deny paths; read-only audit snapshot behavior; both revocation lock orders including session/credential changes; extra/missing/reordered effects and journals; exact cached-response authorization; original-scope history; all current API/browser/worker gates; child-audience substitution; lease expiry/reallocation/five-attempt ceiling and original job deadline; real PostgreSQL scans revoked at claim/redemption/completion; and old-executor drain/prepared-transaction refusal. SQL001–011/checksums and all prior immutable receipt bytes must survive the forward-upgrade gate.

These are acceptance obligations, not executed results. No source, role, SQL, runtime, requirements status or evidence manifest is changed by this design artifact.
