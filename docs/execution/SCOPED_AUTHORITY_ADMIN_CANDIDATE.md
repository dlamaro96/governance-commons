## 1. Decisions proposed for adoption

1. Definitions are inert immutable templates. Publishing a role, responsibility type or policy version never repins an assignment. A group definition changes labels only; membership is a separate exact record. Policy management cannot attach a policy to a subject. Activation uses an explicit role assignment or an explicitly authority-bearing responsibility assignment.
2. A grant carrying an administration action has an additional protected **control ceiling**, described below. An action such as `authority:assign-role` alone cannot mint arbitrary content or administration privileges. Control rights do not grant the administrator access to the controlled content. All self-benefiting changes require an explicit self-benefit allowance; the default is false.
3. Ordinary assignments have immutable issuance provenance and their own current lifecycle. Deactivating their original author does not silently revoke every ordinary grant the author once issued. Delegations and elevations are different: their connected parent authority and issuer eligibility are rechecked at each use, and ancestor revocation defeats dependent use. This distinction must be explicit in storage and evaluator types.
4. A definition retirement succeeds only after all live or future-effective binding dependencies are absent. It never cascades, repins, deletes history, restores a revoked grant or bypasses applicable denies. Revoke grants/memberships explicitly first. There is no definition restore action in the closed registry; a new definition ID may be created under its own authority.
5. Installation and recovery are deployment-only, exact-manifest, one-use trust operations, separate from the human HTTP API. They grant only explicitly enumerated administration capabilities, never content access, FIELD/SERVICE actions, identity activation or a general operator bypass. Recovery repairs an explicit administration defect; it does not reset compatibility grants or reactivate old sessions/executors.

## 2. Common wire shapes and protected semantics

Use the strict UUID, Version, UTC, Digest, Scope, RolePin, PolicyPin, Validity, PolicyDefinition and AuthorityProblem types from the authority contract. An actor/tenant, approved rule match, registry version, timestamps or permission array is never accepted as caller evidence. The selected tenant and actor come from the exact fresh authenticated session. Every object below is closed; nullable fields are present, not optional. Descriptions and reasons are ordinary submitted text, never expressions or trusted facts.

Proposed new-admin-only input bounds: label 1–200 Unicode code points; description 0–4,000; reason 1–500; all well-formed and free of control characters. Immutable definition keys use `^[a-z][a-z0-9_-]{0,79}$`. A command body is at most 128 KiB UTF-8 and its retained normalized form must also fit; policy content separately retains the adopted 64-KiB/128-node/depth-8 limits. Definition policy arrays have 1–32 distinct exact pins; resource-kind/action/field lists are finite, distinct, registered sets. No admin limit reduces existing business profiles or implies a tenant membership limit. Shared aggregate admission/operation budgets remain a prerequisite in section 8.

`ControlCeiling` is a requested child ceiling, never proof that the caller has it. Storage derives the issuer's actual current control records and proves the requested ceiling is contained in their exact authorized scope. Scope containment uses canonical current domains and the requested old/proposed scope, with the adopted maximum ancestry and current field registry; names and client ancestry arrays are not evidence. Action/kind/field inclusion is literal. `fields:null` means no additional field restriction inside that control ceiling, **not** a field grant, sensitive-field entitlement, resource-wide deny or future-action permission. A non-null field set restricts fields affected/disclosed by resulting grants. FIELD actions are not in `HumanActionId`: a supported sensitive-field grant needs an explicit protected companion approved by the sensitivity activation contract; this administration candidate does not invent one.

Control records retain issuer/authorizer provenance, exact grant/version, scope, finite actions/kinds, registry pin, expiry, field ceiling and self-benefit choice. Protected assignment effects retain a literal finite ceiling companion alongside the exact role/policy pins; every resulting atomic request must satisfy both. Do not rewrite a policy AST to approximate an intersection. An ordinary administration mandate is an explicitly issued static control ceiling, not a ceiling inferred from a conditional content allow. Current policy still authorizes the administration action at its destination anchor. A content grant whose authority depends on ongoing issuer predicates must use the connected delegation path rather than being converted into an unconditional ordinary mandate. A control ceiling authorizing administration of content actions is permission to administer those exact actions only; it is not an allow for the administrator to execute them.

Responsibility assignment with `grantsRole:null` requires both `control:null` and `delegable:null`: it creates documentation only. A mapped role follows the complete role-assignment rules, including an explicit non-null child control when it carries ADMIN effects. Delegation of ADMIN effects likewise requires an explicit requested non-null control, attenuated from the exact connected parent's protected control. It never derives control from a policy expression or treats omitted/null control as unrestricted. That delegated control remains bound to every current parent/issuer check; it does not become an ordinary independent administration mandate. A content-only role/responsibility/delegation requires `control:null`.

Definition IDs and version 1 are server-created. Publications carry `target:VersionedTarget`, `expectedDefinitionVersion`, and the next `DefinitionContent`; storage fixes the next definition version and refuses a kind/key change. The head's `version` is the optimistic-concurrency version and is distinct from the exact immutable `definitionVersion`. Publishing/retiring advances the head version; membership changes do not republish a group definition. Each assignment, direct membership, delegation, elevation and elevation-use record has its own immutable ID and version. Active grants are not edited in place: revoke and create a separately authorized replacement. A caller cannot renew an expired grant through a label change.

Policy pins retain the adopted canonical hash of `{formatVersion:1,id,version,rules}`. Resource-wide intents are an immutable protected companion keyed to that exact policy version/hash and pinned registry, additionally hashed into decision/control evidence; they cannot be changed without publishing a new version. Other definition hashes cover canonical `{formatVersion:1,kind,id,version,content}`. A resource-wide intent must name an existing deny rule with `fields:null`, valid canonical resource kinds and the exact finite applicable action expansion; mismatch is rejected, never silently rewritten. The companion supplies the projection catalog's persistent resource-wide intent across references/aliases/registered fields. Ordinary action-specific denies remain action-specific. Human administration cannot publish/assign SERVICE effects through these routes; pure syntax acceptance is not publication authority. Sensitive-field or unimplemented fact predicates likewise cannot activate ahead of their separate approved adapters.

These **new** DTOs do not change an existing asset, receipt or audit projection. ## 5. Anti-escalation and lifecycle rules

Every effect first passes current session, identity/member activity, tenant, canonical kind, ACL/native ceilings and explicit denies. ADMIN permissions have no automatic ten-string mapping. A legacy `admin`/`steward`/`owner` string, a matching name, business ownership, a responsibility label, seed persona or platform-operator identity is never an administration grant. Admin control cannot override field/resource-wide denies or bootstrap a sensitive-field grant. Exact role/policy/type pins and proposed result references must be readable under their declared projection before commit.

**Issuance and self-benefit.** Creation of an inert definition needs its named administration action and R; installation of authority needs the assignment action plus control. Control checks cover the complete reachable effect set, not only the proposed role's label or immediate policy count. A group membership change considers existing group role/responsibility/control grants, so adding oneself or a confederate cannot bypass assignment limits. A role granting ADMIN actions requires a proved child control ceiling; absent that companion the grant cannot administer effects. The requested child ceiling must be a subset of the current issuer ceiling, including explicit self-benefit and validity. Self-benefit means the actor is the direct beneficiary or a current direct member of a benefiting group, including authority regained by removing a deny. It is allowed only when the controlling record explicitly allows it; record that fact in the protected decision. No hypothetical future group membership is inferred; each later membership change is independently checked.

Removing a deny can increase access. Revocation, group removal, policy/role replacement and registry changes therefore evaluate the complete effective change against the control ceiling, even when the UI verb sounds restrictive. Do not approximate policy implication from a few sampled resources or drop ABAC conditions. For ordinary grants, retain the proven issuance constraints as enforceable companions, so a policy expression cannot exercise actions/scopes/fields outside them later. A published definition remains unbound until an explicit assignment uses it. Replacing an assignment is a fresh ID plus explicitly authorized revocation; neither immutable pin nor historical success is overwritten.

**Delegation.** Proposed A1 record limits: maximum four connected delegation edges, maximum 30-day newly issued validity, earliest parent/grant expiry wins, and each child reduces remainingDepth by at least one. Root grants require an explicit delegable ceiling; null means nondelegable. A child cannot expand actions, fields, scope, validity, control or onward depth. Effective use rechecks the issuer's current effective authority and every exact parent grant/version and current beneficiary membership; it cannot rely on an issuance-time allow. No nested groups or delegation to groups/services in this DTO. All principal/fact closure is complete and charged under the shared budgets. The four-edge bound applies only to newly introduced delegation data, not to existing canonical resource/profile counts.

**Elevation.** Proposed A1 lifetime is at most 60 minutes, bounded by every current parent and session expiry; no renewal or onward delegation. Issue targets an already provisioned active tenant member and yields an inactive capability until separately authorized use. A valid `authority:elevation.use` decision on the exact record is required; issuance grants no use permission. At most one active use per elevation, bound to one actual session UUID/version; another use request conflicts unless it is the same currently authorized idempotent replay. An optional use UUID in a future request is only a selector, resolved against that exact session and current record. Do not return or accept an elevation bearer token. Logout, tenant switch, issuer/ancestor revocation, expiry or elevation revoke invalidates use. Already returned bytes are not retractable; mutation linearization follows the storage locks. The administration/recovery channel, not content elevation, is used to repair administration access.

**Retirement.** “Live or future-effective” means an unrevoked binding whose expiresAt is null or later than the current database clock, including notBefore in the future. Definition preview and execution derive complete reverse dependencies through pinned policies, roles, responsibility mappings, groups, delegations and elevations; no caller list/page serves as the cohort. Any such dependency blocks retirement with `ready:false`; the execution must reject it as `AUTHORITY_INPUT_INVALID` with a submitted-target-only `scope` issue. ## 7. One-use installation and recovery

The migration owner is the deployment trust root, not a runtime adversary the database can constrain. Its credential stays outside API/login/service/projector/site processes. The installer uses a separately authenticated deployment channel and protected exact role OID/registration; it never asks a user to paste credentials into chat or accepts a public `bootstrap=true` header, environment string or numeric generation as proof. This proposal specifies provenance for a future tool; **no installation or recovery has been authorized or executed by writing it**.

Proposed closed deployment-only functions are `gc_authority_installation_prepare(operator_session_hash text, manifest jsonb)` → `{installationId,manifestHash,expiresAt}` and `gc_authority_installation_consume(operator_session_hash text, installation_id uuid, manifest_hash text)` → the sealed administration mutation result. No runtime role receives EXECUTE. The original `session_user` must match the exact registered deployment executor role OID and generation. A private deployment-operator registration independently binds that role to the exact operator identity, permitted tenant, purposes and maximum control ceiling. In addition, a current broker-issued operator session, with authentication time no older than five minutes, must prove that same identity and selected tenant; validate its exact provenance, activity and canonical membership. A plain actor UUID or legacy session row is insufficient. Both prepare and consume require that proof, and consumption requires the same operator/registration and exact manifest hash. The session hash is an authentication input and never enters public evidence, logs or Temporal. These are additional trust functions, not a twenty-second human action or a route through the API pool.

The closed input manifest is `{formatVersion:1,requestId,purpose,tenantId,generation,registryDigest,expectedAuthorityEpoch,expectedStateDigest,beneficiaryIdentityId,adminActions,scope,control,validity,reason}`. `purpose` is only `initial-admin` or `recovery-admin`; `adminActions` is a nonempty distinct finite subset of the exact 21 actions, `scope` is an authority-resource scope, `control` is a non-null ControlCeiling, and `validity` is an expiry-required interval subject to the ceilings below. All other scalar types and body bounds are those in section 2. Reject an unknown purpose, extra key, stale state or unsupported effect. The protected preparation derives operator identity and exact current membership versions; it must not accept them as claimed proof. It allocates the exact policy/role/assignment IDs once, constructs an inert single-rule administration-only policy and role pinned to those actions/scope, and binds the resulting exact definition hashes and assignment/control into the protected installation plan. `manifestHash` covers both the full input and that derived plan; an ID alone cannot authorize a different plan. The runtime policy AST never becomes a place to encode the operator proof.

The canonical private installation record binds `{installationId,tenantId,generation,registryDigest,purpose,requestId,manifestHash,operatorRegistrationId,operatorRegistrationVersion,operatorIdentityId,operatorSessionId,operatorSessionVersion,beneficiaryIdentityId,membershipVersion,expectedAuthorityEpoch,expectedStateDigest,issuedAt,expiresAt,consumedAt}` plus normalized exact plan and success companions. The beneficiary is an existing current active tenant-member resolved by UUID and issuer provenance, not a role label. Revalidate operator, beneficiary, registration and exact session using the storage lock order. Preparation is an immutable one-use authorization record, with its own protected deployment event; it creates no effective grant. Consumption creates the planned immutable definitions, assignment and paired journal atomically, as described below. An exact preparation retry with the same operator/requestId/body returns its independently reauthorized record; different content conflicts. These records are neither readable nor mintable by runtime roles. Provisioning the separate operator registration and trusted issuer precedes this protocol; this protocol cannot bootstrap its own authentication evidence.

Proposed lifetimes: installation/recovery authorization must be consumed within 15 minutes; the initial administrator grant expires within 24 hours; a recovery administrator grant expires within 30 minutes. These are new trust-operation ceilings, not changes to ordinary role-assignment validity. A subsequent explicitly authorized normal administrator assignment may be durable when its proven control ceiling explicitly allows unbounded validity; bootstrap itself is not a perpetual hidden grant. The manifest may authorize administration of an explicitly listed compatible content-action set through its **control ceiling**, but grants the beneficiary no ability to execute those content actions. No FIELD or SERVICE rights or sensitive-field authority are installed. If content control is omitted, the administrator has no permission to create content grants merely because its role is named administrator.

Initial installation requires the protected per-tenant initial-admin marker to be absent, the exact reviewed current generation/registry and compatibility-state digest to match, and one-use proof consumption in the same transaction as the grant, revision, paired audit/outbox and marker. A repeat invocation returns only its independently reauthorized existing result or refuses; it never reseeds/recreates missing grants. Preserve every existing identity UUID, issuer/subject, role label, active flag, explicit ten-string permission set, revoked grant, immutable version and historical actor. Compatibility migration uses only actual current permission arrays under the already selected mapping, never these new administration rights. Inactive memberships remain inactive, and later revocation must survive seed/migration repetition.

Recovery requires a **new** deployment authorization bound to the exact diagnosed tenant/generation/state digest and finite intended repair; reusing an initial manifest is invalid. It does not turn a revoked normal grant back on: install a new short-lived administration-only record with linked recovery provenance, perform separately authorized exact repairs, then revoke/expire it. Installation does not suppress an explicit deny. If an existing deny defeats every intended repair action, this two-function protocol cannot remove it: a separately reviewed exact forward repair is required, with protected before/after evidence, complete deny-removal impact and preserved unrelated/content denies. Do not silently revoke a mixed content/administration deny as a recovery shortcut. Installation cannot activate identities, create tenant memberships, change issuers, assign service credentials, clear original operation deadlines, reset lease attempts, lower generation, skip old-executor drain or restore broad legacy table access. Such provisioning/deployment operations require their separate closed trust adapters, not one of the 21 human admin actions.

The installer refuses a stale digest, wrong tenant/generation, expired/consumed proof, inactive beneficiary, unaccounted dependency, unresolved prepared transaction or unavailable required audit path. All effects roll back together. Deployment failure leaves authority fail-closed and original failed evidence preserved. No automatic “if no admin remains, become admin” code path exists. A private local recovery file may contain exact recovery instructions and authentication references, but no bearer/credential is added to public evidence. Public records can expose only the registered safe operation result under current authority.
