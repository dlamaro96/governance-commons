# Protected authentication storage foundation — review proposal

Status: **PRIVATE DRAFT; NOT DDL, NOT IMPLEMENTED, NOT EXECUTED, NOT A RUNTIME ACTIVATION.** Prepared 2026-11-16 for root adoption. No migration number is allocated here. Root owns the shared contract, role setup and eventual migration allocation. The complete BUILD_SPEC, existing requirement outcomes and all later authority work remain mandatory.

## 1. Exact increment and accepted refinement

Implement only protected executor/issuer provisioning, provisioned identity binding, one-use login attempts, private sessions with UUID/version provenance, an inactive tenant generation fence, and six narrowly typed authentication functions. Authentication success proves the current session and membership only. It produces no permission array, grant, policy decision, resource scope, authorized projection of content or DecisionBundle. No application route, database pool, worker, projector, service credential, deployment-admin grant or legacy evaluator changes in this increment.

Root explicitly accepted this refinement on 2026-11-16: **protected sessions are independent of public.sessions**. They use the same lowercase SHA256 transport-hash grammar, but there is no legacy session insert, update, FK, dual write, retrospective certification or import. The immutable provenance companion refers to the new private session UUID. This supersedes the older storage candidate's phrase “unique existing session hash.” A legacy gc_app process can SELECT/INSERT/UPDATE/DELETE its session table; sharing that table would expose authentication inputs and permit legacy acceptance/tampering. An independently private session fixes that boundary without touching any old row or migration.

The only representable tenant authority mode is `inactive`. Authentication-only inspection and lifecycle operations can work for explicitly installed test/broker executors in that mode; content remains unavailable. There is **no function, argument, grant, row flag or permissive fallback that changes a tenant to compatibility/scoped authority**. A later reviewed forward migration must introduce those states together with the complete A1 cutover and old-executor drain. Migration creates empty protected infrastructure, no enabled registration, session, issuer, identity binding or seeded tenant fence. Existing core remains untouched.

## 3. Closed scalar contract

All public SQL arguments are scalar SQL types below; all responses are named composite rows, not JSONB. No untyped object, JSON extension bag, dynamic table/function identifier, caller-authored actor, permission, tenant proof or decision is accepted.

Clock proposal: attempts live300seconds; consumed attempts may issue only before their original expiry and within60seconds of committed consumption. Maximum protected session duration1800seconds from issue, no sliding renewal. Broker-attested token must have exp>database clock, iat within the attempt window allowing at most30seconds skew, auth_time<=iat<=database clock; the30second allowance applies only to the lower attempt-window bound, and a finite exp>iat. Neither iat nor auth_time may be future-dated. Session expiry is issue+1800seconds (clamped to executor/issuer/binding hard expiry); token expiry is evidence checked at issuance, **not** silently substituted for the existing thirty-minute browser-session lifetime. Any future shorter product policy is explicit. Unknown/future algorithm is rejected; broker uses RS256 only.

auth_time is required for the protected protocol. It must come from a verified token claim; iat, database issue time and caller wall time cannot fabricate recent authentication. Existing legacy broker lacks this requirement and stays unchanged. Until a separately qualified broker/IdP configuration supplies auth_time, no live protected issuance is connected. This is necessary for later five-minute deployment/admin elevation proof.

## 4. Ownership, privilege and installation arrangement

Private schema: `gc_authn`, owned by existing migration owner gc_owner. Tables are owned by gc_owner, which remains NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOINHERIT/NOBYPASSRLS. A separate `gc_authn_definer` is NOLOGIN/NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOINHERIT/NOBYPASSRLS and owns only the six public authentication entrypoints and their private composition helpers. It receives enumerated table/column privileges, no schema CREATE, no tenant-content privileges, no arbitrary writer function and no installation function.

A cluster-admin setup step creates the NOLOGIN definer and exact new LOGIN executor roles before migration. It grants gc_owner a **temporary SET-only, non-admin, non-inheriting membership** in the definer solely for the reviewed function-ownership transfer, then removes that membership and any temporary schema CREATE immediately after migration. Read back the final graph. The executable setup must use PostgreSQL17 membership options explicitly; never assume NOINHERIT prevents SET ROLE. No runtime executor is granted any membership in another executor, owner or definer, in either direction. No executor can create roles, databases, schemas, tables, functions, extensions or temporary objects via granted database TEMP. The inactive qualification profile requires max_prepared_transactions=0: there is no per-role PREPARE TRANSACTION privilege to revoke. A profile permitting prepared transactions requires a separate reviewed protocol and the eventual explicit drain check. Reject an unexpected membership rather than trying to repair it inside login functions.

Foundation executor kinds are only `login` and `api`. A separate real role name such as gc_a1_login_g1 is merely a deployment label. `session_user::regrole::oid`, exact stored role name, actual LOGIN/privilege bits, empty membership adjacency and registration generation identify a connection. Definer current_user, numeric generation arguments, role-name prefixes, application_name and all gc.* GUCs prove nothing. Drop/recreate under the same name changes OID and refuses; rename refuses until a new reviewed registration. Cluster administrators are explicit trust roots, not constrained adversaries.

Login roles get CONNECT and USAGE on public only, no table/sequence/private-schema access, no default function grants. Grant only exact signatures from section7. `gc_authn_definer` receives USAGE on gc_authn and enumerated privileges there, SELECT(id,issuer,subject,active) on identities, SELECT(tenant_id,identity_id,active) on memberships, and SELECT(id) on tenants. It does not receive legacy session/login_state DML or content access. Public-session collision checking, if retained, uses a narrowly scoped owner helper exposing only existence, never hash/table reads to a runtime role; collision checking is defense in depth, not the private boundary.

Every SECURITY DEFINER uses fully qualified objects, fixed `search_path=pg_catalog,gc_authn,pg_temp`, `row_security=on`, no dynamic SQL and no user-resolved operator/function. PUBLIC EXECUTE is revoked in the same DDL transaction as creation, including helpers and overloads. Default privileges for newly created functions/types/schema objects are made explicit without changing existing legacy grants. PUBLIC and old gc_app get no new privileges. Runtime roles get USAGE on only the exact public return types required for their functions. Forward DDL must use a frozen finite census of existing public.gc_* signatures to revoke residual PUBLIC EXECUTE while granting their prior effective gc_app execution explicitly, preserving legacy behavior. New executors inherit no legacy callable path through PUBLIC. No wildcard dispatcher/revocation is a substitute for that reviewed list. Root captured the actual read-only predecessor census at `.local/evidence/authority-storage-foundation-integration/legacy-function-census.json`, SHA256 `a2affa4c201bd03c23bdf91ed7f765fcbcde0cb3c351c13607be405ba3cfb51e`:155 public gc_* functions,56 with PUBLIC EXECUTE, exact signatures/owners/definer flags/effective gc_app rights and11 migration digests. Freeze exactly those56 signature revokes plus explicit gc_app grants, preserve all155 effective gc_app rights, and compare the isolated preupgrade catalog to this census before DDL. This root-provided read-only observation is not a foundation execution gate. authn_definer receives only gc_tenant()/gc_actor() execution needed by existing membership RLS; it receives no legacy content helper. No grant on ALL TABLES/FUNCTIONS/SEQUENCES is allowed. Schema/type lookup attacks and every callable overload are included in the privilege census.

The migration refuses missing/wrong prerequisite role flags/owners/memberships, preexisting conflicting protected objects, wrong predecessor checksums or unexpected old-role membership in the owner. Role setup is separate from transactional DDL. A setup failure leaves roles disabled and does not alter core. Migration may neither create/alter a LOGIN role nor enable one.

## 5. Proposed normalized tables and constraints

This is a logical SQL schema specification, not executable DDL. Every listed column is NOT NULL unless marked `?`. UUID references are non-nil. Every FK defaults to NO ACTION; no cascade may erase evidence. All revocation is monotone. All new tables/columns have explicit privileges; no runtime has TRUNCATE, REFERENCES, ownership, DML or raw SELECT. Triggers reject DELETE and forbidden updates independently of ordinary grants. Root may adjust names before freeze, but not omit fields silently.

### Global private deployment and authentication infrastructure

0. **gc_authn.installation_root**: `singleton boolean PRIMARY KEY CHECK singleton; database_oid oid; owner_role_oid oid; owner_role_name name; contract_hash text; installed_at timestamptz`. The migration inserts exactly one immutable row using actual current_database() catalog OID and original session_user OID after checking it is the intended non-superuser owner. contract_hash pins the separately adopted contract bytes (not an impossible self-hash of this migration); actual migration file digests remain in the existing migration ledger and source-bound upgrade report. No public provisioner supplies or modifies it. Every deployment function compares original session_user and database OID to this pinned row, not merely caller expected OIDs or a role name. The schema owner remains a trust root that could change DDL; this records authenticated installation provenance, not protection from the migration owner.

1. **gc_authn.installation_receipts**: `id uuid PK; request_id uuid UNIQUE; deployment_database_oid oid; owner_role_oid oid; owner_role_name name; operation text; target_id uuid; manifest_hash text; manifest_encoding bytea; predecessor_hash text?; release_reference text; deployment_operator_reference text; recorded_at timestamptz`. operation is the closed enum `register-executor|advance-generation|advance-tenant-generation|register-issuer|bind-identity|initialize-tenant|revoke-executor|revoke-issuer|revoke-binding`. manifest_hash is recomputed from the exact typed request plus resolved OIDs, database OID and expected prior state. manifest_encoding retains the exact closed domain-separated tuple preimage (≤65536bytes), assembled internally from scalar typed arguments and resolved records, never a supplied bytea/JSON payload. It allows historical hash recomputation even after heads advance. These rows are immutable deployment events; target rows retain normalized typed state. Idempotency `(request_id,manifest_hash)` returns only the same record after revalidating deployment authority; differing content conflicts. A later operation never mutates an earlier receipt. No human identity assertion is made from deployment_operator_reference: the authenticated deployment database role and external release record are the trust source. This is separate from later admin-installation prepare/consume.

2. **executor_registrations**: `id uuid PK; role_oid oid UNIQUE; role_name name UNIQUE; kind text CHECK login|api; generation integer; installation_id uuid UNIQUE FK installation_receipts; installed_at timestamptz; expires_at timestamptz; revoked_at timestamptz?`. UNIQUE(kind,channel_id,generation); UNIQUE(id,kind,generation). expires>installed. Immutable except null→revoked_at, with revoke receipt companion below. Registering is not enabling: current head must separately select it. Actual role must have expected safe bits and no memberships. One role serves exactly one kind and generation; no OID reuse across generations.

3. **generation_heads**: `kind text CHECK login|api; channel_id uuid; generation integer; executor_registration_id uuid UNIQUE; version integer; installation_id uuid FK installation_receipts; advanced_at timestamptz; PRIMARY KEY(kind,channel_id)`; FK(registration_id,kind,generation)→executor_registrations. A new head requires strictly greater generation, a new exact role and expected previous version/OID. Initial head requires absent row, version1. No reset/delete. Login and API generation must agree with the selected tenant fence for authentication. Head changes invalidate former executors even on already-open connections; no claim that they close those connections. Later A1 drain remains mandatory.

4. **issuer_registrations**: `id uuid PK; executor_registration_id uuid UNIQUE FK executor_registrations; generation integer; issuer text; client_id text; redirect_uri text; environment text CHECK isolated-test|local-development|production; installation_id uuid UNIQUE FK installation_receipts; installed_at timestamptz; expires_at timestamptz; revoked_at timestamptz?`. FK(executor_registration_id,'login',generation) is realized with a fixed checked executor_kind column and composite FK. One exact issuer/client/redirect per login role/channel. Multiple current channels permit multiple issuers without a tenant/issuer count cap. No mutable endpoint or broker reassignment. URLs are not read from request headers. Retire/new version for configuration changes.

5. **identity_bindings**: `id uuid PK; issuer_registration_id uuid FK issuer_registrations; identity_id uuid FK public.identities; subject text; canonical_issuer text; version integer CHECK=1; installation_id uuid UNIQUE FK installation_receipts; installed_at timestamptz; expires_at timestamptz; revoked_at timestamptz?`; UNIQUE(issuer_registration_id,subject), UNIQUE(issuer_registration_id,identity_id), UNIQUE(id,identity_id). Provisioning verifies exact existing identities(id,issuer,subject) equality; every issue/inspect/select repeats it and requires active. No JIT identity creation, name-based match, subject rebinding, active-flag change or membership insertion. New issuer generation gets an explicit new binding to the same existing identity UUID, preserving canonical provenance. Revoked bindings never reactivate; a separate new issuer/binding registration is required.

6. **login_attempts**: `id uuid PK; state_hash text UNIQUE; nonce_hash text; issuer_registration_id uuid FK issuer_registrations; executor_registration_id uuid FK executor_registrations; generation integer; verifier text?; created_at timestamptz; expires_at timestamptz`. Exact issuer/broker/generation association validated at insert. expires=created+300s. Immutable binding columns; verifier is present only until committed consumption, then null. No state/nonce/verifier/token appears in events or external logs. No identity/tenant is asserted by an unauthenticated attempt.

7. **attempt_consumptions**: `attempt_id uuid PK FK login_attempts; executor_registration_id uuid FK executor_registrations; generation integer; consumed_at timestamptz; consumed_transaction_id xid8; issue_deadline_at timestamptz`; exact same executor/generation as attempt; deadline=min(attempt.expiry,consumed+60s). Immutable. consumed_transaction_id is obtained from pg_current_xact_id(), never supplied. Issue requires a different current transaction ID; the visible row must therefore come from a committed transaction under required READ COMMITTED. Insert and verifier erasure occur in one transaction; concurrency uses locked attempt row/unique PK. A rolled-back SQL transaction has not consumed an attempt. The trusted broker MUST commit consumption before external token exchange; it cannot span the network exchange in that transaction. This necessary protocol obligation is explicit, not a false autonomous-transaction guarantee.

8. **sessions**: `id uuid PK; session_hash text UNIQUE; identity_id uuid FK public.identities; selected_tenant_id uuid; csrf_hash text; version integer; generation integer; issued_at timestamptz; authenticated_at timestamptz; expires_at timestamptz; revoked_at timestamptz?`. Globally private because one authentication session can switch between memberships; selected tenant is a current locator, not table ownership.

Entire row immutable. Deferred/closed function invariant proves exact issuance tuple and current session projection against subsequent session_events; an arbitrary hash match is insufficient. Stores digest only, no raw JWT, authorization code, bearer or CSRF.

10. **session_events**: `session_id uuid; version integer; kind text CHECK issued|tenant-selected|revoked; identity_id uuid; previous_tenant_id uuid?; selected_tenant_id uuid; csrf_hash text; occurred_at timestamptz; executor_registration_id uuid; executor_role_oid oid; generation integer; PRIMARY KEY(session_id,version)`; FK(session_id,identity_id)→sessions; FKs for both non-null tenant/member pairs, executor registration. issued version1 has null previous tenant; select has previous tenant and version>1; revoke preserves tenant/CSRF and increments version. 11. **registration_revocations**: `installation_id uuid PK FK installation_receipts; target_kind text CHECK executor|issuer|binding; target_id uuid; revoked_at timestamptz`; closed per-kind CHECK/FK implementation uses three nullable typed FK columns with exactly one non-null, not an unvalidated polymorphic FK. UNIQUE each non-null target; target row and receipt state updated atomically. No revoke operation expands authority or changes legacy identity/member rows.

### Tenant-owned state

12. **tenant_fences**: `tenant_id uuid PK FK tenants; mode text CHECK(mode='inactive'); generation integer; epoch integer; installation_id uuid UNIQUE FK installation_receipts; initialized_at timestamptz`; initial epoch1. ENABLE and FORCE RLS. Foundation provides absent→inactive initialization and exact owner-only advance-tenant-generation. The latter requires expected current epoch+generation, strictly greater target generation, current compatible API/login channel heads at that target, and at least one live API channel and one live issuer/login channel at the target generation. It preserves inactive mode, increments epoch once and forces fresh sessions. No mode activation, reset, lower generation or content-policy epoch mutation is available. The owner operation follows tenant-ledger then fence lock order and never silently rolls all tenants forward. Missing/stale fence denies authentication inspection/selection for that tenant. No tenant population cap; initialize each approved tenant independently.

Global records above are **explicit global private trust infrastructure**, not tenant content. Do not disguise them as tenant-owned by copying a current selected tenant onto an issuer/attempt/session primary key. Their protection is absent runtime privileges, exact callable interfaces, immutable provenance and role separation. Tenant fence is forced-RLS with explicit tenant predicates. Policy for the definer permits only the protected-derived selected tenant; deployment owner has an explicit all-row provisioning policy because it is the trust root. Never grant runtime TRUNCATE or REFERENCES on forced-RLS tables: RLS does not constrain those operations.

### Private lock helpers — no canonical UPDATE grant to the authentication definer

PostgreSQL row-locking SELECT requires UPDATE privilege on at least one target column. SELECT-only access to identities/memberships cannot support FOR SHARE. Do not silently remove locks or grant broad canonical UPDATE. Add owner-owned SECURITY DEFINER helpers with row_security=on and the same fixed fully qualified search path:

* `gc_authn.lock_configuration(executing_registration_id uuid, issuing_registration_id uuid, issuer_id uuid, binding_id uuid, tenant_ids uuid[]) RETURNS void`. Exact optionality is operation-derived: issuing/issuer/binding may be null before an attempt or binding resolves; tenant_ids is a distinct sorted array of0..2 non-nil UUIDs. Locks current heads in `(kind,channel_id)` order, exact registrations in UUID order, exact issuer/binding if present, then tenant fences in UUID order. It checks registration association and rejects unexpected missing rows. No returned data or DML. Call only from the fixed authn functions; no generic content configuration locking.
* `gc_authn.lock_principals(identity_id uuid, tenant_ids uuid[]) RETURNS void`. Single non-nil identity, distinct sorted1..2 non-nil tenant UUIDs (one for issue, at most two for select); locks identity first then exact memberships sorted tenant. No active filter: caller rechecks activity after waits. These are fixed operation operands, not population limits. Save/derive/restore actor/tenant GUCs on all exits, explicit predicates and forced RLS, no dynamic SQL, no returned data/DML. Called only after configuration/fence locks.

Only owner and gc_authn_definer may EXECUTE; PUBLIC/gc_app/login/api cannot. The definer has UPDATE only on its own attempt/session lifecycle tables needed for exact row locks, never canonical identity/member UPDATE. Runtime functions call configuration helper first, then principal helper where appropriate, then lock exact attempts/sessions through their own narrow existing DML privileges. Owner provisioning uses the same sorted configuration row order; advance-tenant-generation additionally takes the existing tenant ledger before configuration/fence acquisition. Later full content composition must preserve the adopted global lock order; no content function is installed here.

### Exact channel and generation relationship

Head primary key is `(kind,channel_id)`; registration uniqueness is `(kind,channel_id,generation)`. A composite channel FK additionally requires the selected head registration to have the same channel_id. Issuer registration binds one login channel; API channels are separately provisioned. All channels used for a session have the same deployment generation selected by tenant_fences. A session records its login issuer channel through the immutable issuing registration; inspection may use an enabled API channel at that same generation. The exact issuing registration must remain live/current. No caller can choose a channel as proof: session_user OID resolves it. This preserves configurable multiple IdPs without role-name wildcards or an issuer/population cap.

## 6. Exact installation manifests and private provisioning API

Provisioning is a separate authenticated deployment process; no API/login executor may invoke it. Original session_user must equal the exact migration-owner OID installed by the migration, with safe flags verified. It must not be an owner reached by SET ROLE. Cluster role setup is separately authenticated and recorded; no credential value/hash is embedded in manifests, receipts, reports or shell arguments. This initial trust installation cannot depend on the broker it is creating. Later content-admin install/recovery remains the distinct fresh operator-session protocol in ADMIN candidate section7.

Each manifest contains exactly `formatVersion:1, requestId:UUID, releaseReference:Ref, deploymentOperatorReference:Ref, expectedDatabaseOid:RoleOid, expectedOwnerRoleOid:RoleOid, predecessorManifestHash:Digest|null, operation:Operation` and one of these closed operation objects. The tool expands only validated parameters into parameterized SQL; raw JSON is never passed to a SQL dispatcher. No generic arbitrary `payload` exists. A collection is an ordered file of independent manifests, not a grant scope; splitting provisioning batches never changes a business scope or silently truncates tenants/identities. Duplicate request IDs with different bytes refuse. Raw input parsing uses the existing duplicate-aware bounded file admission before materialization, with exact closed discriminated schema, and a64KiB per-manifest physical limit. This new provisioning limit is not a principal population limit.

* register-executor `{registrationId,channelId,roleName,expectedRoleOid,kind:'login'|'api',generation,expiresAt}`.
* advance-generation `{kind,channelId,registrationId,expectedPreviousRegistrationId:UUID|null,expectedHeadVersion:Version|null}`; no mixed-null pair.
* register-issuer `{issuerId,registrationId,generation,issuer,clientId,redirectUri,environment,expiresAt}`.
* bind-identity `{bindingId,issuerId,identityId,expectedCanonicalIssuer,expectedCanonicalSubject,expiresAt}`.
* initialize-tenant `{tenantId,generation}`; no permission/role/membership creation.
* advance-tenant-generation `{tenantId,expectedGeneration,expectedEpoch,generation}`; strictly greater generation, current compatible configured channel heads, inactive mode preserved, epoch+1. A target generation requires at least one live API channel and one live issuer/login channel; there is no requirement to rotate unrelated channels not used by this tenant. Any old-generation session fails the fence; channels themselves remain exact and independently current.
* revoke-executor `{registrationId}`; revoke-issuer `{issuerId}`; revoke-binding `{bindingId}`. Revoke records database time; supplied revocation timestamps are forbidden.

## 8. Read-only, RLS, race and transport obligations

Inspect runs within a fresh primary **READ ONLY REPEATABLE READ** transaction. No INSERT, UPDATE, DELETE, row lock, audit/outbox write, transaction-context table, untrusted authority GUC, replica or externally selected snapshot. It may install transaction-local actor/tenant settings only after resolving the private session, solely for the existing membership RLS SELECT. Save original values, set both from protected data, and restore on success/error; a helper cannot leak a privileged value to a following call. Caller GUCs are ignored. Explicit predicates still constrain identity and selected tenant. The private global lookup has no public/table return path. RLS can use a definer-only protected-derived tenant GUC for tenant_fences because no executor can SELECT that table or SET ROLE into the definer.

Read success linearizes at its fresh snapshot; pre-snapshot committed revocation is observed. Same-snapshot subsequent mutations are not promised visible. Database expiry is checked at return. No reuse of a transaction/snapshot across requests. The database cannot authenticate “fresh HTTP request” from arbitrary client SQL; the future trusted adapter must open the correct transaction. This authenticated_session row grants no business authority even if a caller retains it. Mutations use READ COMMITTED with lock-and-reread and reject incompatible isolation; test races independently. This foundation does not claim the future thirty-second command deadline or a non-resettable content transaction lease. It enforces only its explicitly stored attempt/consumption/session expiries at the documented checks; deferred commit deadline enforcement and content operation fencing remain later work.

Canonical identity/member deactivation already serializes on their own rows; no new reverse-order tenant locks are added to those update paths. Issuance/select take FOR SHARE as needed, conflicting with deactivation; session revoke/select serialize on the exact session row. Registration/issuer revocation races need a deterministic order too: deployment generation/head/issuer/binding share locks first, then tenant fences, identities, memberships, authentication rows. All mutations recheck after lock waits and before returning, using database clock. Revocation that wins first denies; operation that wins may commit before revoke. Read inspection takes none of those locks. Concurrency tests must prove both outcomes without asserting instant retraction of returned bytes.

Future broker transport: raw session and CSRF are independent32-byte random base64url values. Session cookie remains HttpOnly/SameSite/secure-production; raw CSRF exists only in a separately named JS-readable SameSite/secure-production cookie (or explicitly reviewed equivalent transport), sent as a header with exact Origin validation. DB receives only their hashes. Tenant select supplies the replacement CSRF hash and updates that transport cookie after commit. Never reuse legacy /me's raw database csrf field or store raw CSRF in protected records. New cookie name such as `gc_authority_session` is mandatory until atomic cutover; inactive foundation provides no HTTP integration at all. Raw/hash authentication inputs never enter logs, public evidence or Temporal.

Private append-only installation and session events are security-infrastructure evidence, not legacy content-audit envelopes or outbox messages. No content mutation occurs, so no legacy journal schema is rewritten or fabricated. Later registered security-event export/audit integration and retention policy are still required. Attempt verifier deletion on consume is required now; expired abandoned attempts can retain verifier until a separately adopted owner-only bounded purge job is implemented. Do not claim retention minimization/SCIM/deprovisioning or full audit qualification from this foundation.
