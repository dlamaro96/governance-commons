# ADR0006 — Complete type migrations and immutable policy receipts

Status: implemented; isolated SQL007 upgrade/storage/concurrency and rebuilt core API gates pass. Targeted and full 12-journey browser acceptance pass for the recorded development scope. Full M2 and release qualification remain open.

An authored asset type carries inherited fields, required ownership and lifecycle policy. An attribute-only migration cannot describe or prove a change to all three. Keep the existing attribute plan and legacy receipt format intact, and compose a strict outer plan with exact owner overrides, source-version state mappings and explicit policy acknowledgements. Every directly bound asset migrates in one bounded transaction; descendant type and asset pins remain unchanged.

The execution locks idempotency, tenant ledger, model scope/head, assets and then principals in deterministic order. PostgreSQL requires UPDATE privilege for row-share locks. A narrowly scoped security-definer function grants only the ability to lock existing principals with membership in the current tenant; it grants no identity writes or tenant-selection mechanism. Its owner must be a non-bypass role unavailable to the application. The function locks inactive rows too, so an explicit owner repair and any concurrent revocation have a stable ordering. Authorization and owner eligibility are reread after waits. Timeouts roll back and return an explicit retryable result.

The original migration receipt retains the unchanged nested attribute plan and normalized revision references. A companion records the immutable type UUID, full plan, source and target hashes, complete before/after tuples and their canonical hashes. Database checks compare the tuples to actual immutable snapshots. Deferred completeness rejects an authored-type base receipt without its companion. Parent-derived normalized rows have exact membership guards, forced RLS and immutable privileges. Legacy receipt routes reject the incomplete representation of authored-type migrations.

Preview consent binds the entire cohort, exact resolved ancestry, plan and current/proposed owner activity. Changed definitions, state, ownership, eligibility, versions or cohort require a fresh preview. Successful idempotency replay still checks current permissions and visibility of the original recorded assets. All canonical writes, revisions, audit, outbox and success receipts commit together; a failed attempt can append only a separate bounded, redacted failure audit.

The SQL canonical serializer is scoped to the supported plan/tuple contract: safe ASCII object keys, JSON strings and finite JSON numbers in JavaScript notation. Decimal attributes remain strings. It is not a general JSON canonicalization standard. Cross-runtime number/string tests and immutable-snapshot comparisons are required qualification, together with both revocation lock orderings and late rollback.

The synchronous profile retains 1,000 assets, 64 attribute operations, 512KiB aggregate plan/definition/value materialization and 100,000 nodes. Preview also measures actual PostgreSQL JSONB text sizes because exponent notation expands in storage: 8 MiB each for plan and receipt assets, 256 KiB for the authored definition and 512 KiB for its resolution. Exceeding a bound fails before writes. Durable large-cohort migrations, production backup/restore, constrained relations, other model kinds and the remaining programme are separate required work.
