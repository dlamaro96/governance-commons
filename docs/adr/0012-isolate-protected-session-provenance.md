# ADR0012: Isolate protected session provenance from legacy sessions

Date: 2026-11-16. Status: accepted and implemented as inactive SQL012; isolated native qualification passes. Protected OIDC transport, content authority and cutover remain open. See [scoped evidence](../verification/authentication-foundation.json) and [current runtime state](../execution/STATE.md).

The existing application role can read, insert, update and delete `public.sessions`. Authentication currently reads that table directly. Attaching a new issuance certificate to an existing session hash would therefore make the protected protocol depend on a tuple the legacy executor can change. The new authentication boundary must also prevent a newly issued protected session from falling through to legacy authentication before the coordinated authority cutover.

Store new sessions and their immutable issuance provenance in private authority tables. Keep a new session UUID and monotonic version independently of the opaque transport token's SHA-256 hash. Do not insert a matching legacy session or certify an old session retrospectively. Preserve all existing legacy rows and historical business records. New entrypoints resolve their session only through the private store; legacy authentication continues to use only its existing store. Require fresh sign-in at the eventual cutover.

The dedicated OIDC broker proves an exact configured issuer, client and one-use attempt. Its separately provisioned database login is registered by actual role OID and generation. Protected entrypoints validate the original login role (`session_user`), rather than accepting a role name, GUC, actor ID or the changed `current_user` inside a definer function as proof. Executor memberships, function signatures, schema privileges and defaults are part of the installation check. `NOINHERIT` alone does not exclude `SET ROLE`; PostgreSQL documents these as separate membership capabilities. [Session identity](https://www.postgresql.org/docs/17/functions-info.html), [role membership](https://www.postgresql.org/docs/17/role-membership.html).

The foundation will expose only closed authentication lifecycle envelopes under its inactive mode. It will not return a generic decision bundle, policy snapshot, permission array or tenant content. Hashes supplied by the broker remain authentication inputs and must not enter logs, public evidence or workflow payloads. Raw CSRF material belongs to the future browser transport; storing its digest does not authorize returning that digest as a replacement CSRF token. Transport integration requires its own cookie, origin, CSRF and browser acceptance gates.

This explicitly supersedes the storage candidate's proposed linkage to an existing session hash row. The candidate remains preserved as design history. Exact schemas, issuance/selection/revocation rules, provisioning commands and lifetime/locking constraints must be frozen in the foundation contract before forward DDL is allocated. Existing SQL001–011 remain immutable. Runtime database roles remain nonowners without bypass-RLS privileges; definer entrypoints require trusted search paths and explicit execution grants. [Definer precautions](https://www.postgresql.org/docs/17/sql-createfunction.html), [row-security boundaries](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

Separate tables deliberately create a transition boundary. No dual-read fallback is permitted after activation. The later A1 cutover must implement every registered ingress, revoke old access, drain old connections, refuse unresolved prepared transactions and qualify current authorization, effects, projections and revocation. An inactive authentication foundation, passing reference evaluator or successful sign-in alone does not meet that gate. Policy administration, installation/recovery grants, service leases, SQL/OpenSearch equivalence and the remaining full programme remain required.
